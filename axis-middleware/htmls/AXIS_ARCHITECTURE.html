Architecture intent

Axis sits between the application middleware and the data infrastructure. The middleware is responsible for HTTP and identity, while Axis owns the semantic interpretation of a request and decides how that request should be fulfilled.

The architecture intentionally separates the user-facing read path from background synchronization. OpenSearch is the optimized search representation, PostgreSQL remains the transactional source of truth, S3 holds static or precomputed aggregates, and the embedding service converts searchable text into vectors.

Core components

Middleware

HTTP routing, authentication, request context and application wiring. It does not construct backend-specific queries.

Axis

Semantic layer containing models, query interpretation, planning, caching, backend compilers, indexing and normalization.

Query Planner

Chooses the appropriate execution path after the request has been validated and resolved.

OpenSearch

Read-optimized store for documents, filters, aggregations and vector similarity search.

Embedding Service

Converts text into vectors. It can use Hugging Face, a local model or another configured provider.

PostgreSQL

Transactional source of truth. Its data feeds the search index through background synchronization.

S3

Stores static or precomputed aggregate data that can be returned without rebuilding the aggregation.

Cache

Existing performance layer. It remains independent from OpenSearch and can short-circuit repeated queries.

Cron

Runs background synchronization so changed source records are reflected in OpenSearch.

Two operating paths

User read path

Frontend → Middleware → Axis → Query Planner → Cache / OpenSearch / Embedding → Response

This path is optimized for request latency. Existing indexed documents are read directly from OpenSearch. For semantic search, only the user's query needs to be converted into an embedding before the vector search is executed.

Background synchronization path

Cron → Axis SQL pipeline → PostgreSQL → Document preparation → Embedding → OpenSearch

This path keeps the search representation synchronized with the source database. It is deliberately outside the normal user request path so indexing and embedding work do not become part of every dashboard request.

Architectural decisions

  • Axis owns backend query translation. Middleware does not build SQL or OpenSearch queries.
  • OpenSearch is integrated into Axis. It is an infrastructure dependency behind Axis configuration and adapters.
  • SQL remains in Axis. It is primarily used for background synchronization and source-data operations.
  • Semantic search does not require an LLM. An embedding model is sufficient for vector generation.
  • Document embeddings are generated during synchronization where possible. Normal semantic requests only need to embed the user's query.
  • PostgreSQL remains authoritative. OpenSearch is the search representation, not the transactional source of truth.
  • S3 is for static/precomputed data. It is not used as the general transactional data store.
  • Caching remains independent. OpenSearch does not replace the existing cache layer.
