AXIS — DATA & QUERY WORKFLOW

How source data becomes searchable, how scheduled synchronization keeps OpenSearch current, and how frontend requests travel through Axis to the correct data source.

1. End-to-End Workflow

The background flow prepares searchable data while the application flow serves user requests. Keeping these flows separate prevents indexing and embedding work from becoming part of the normal request path.

Core boundary: PostgreSQL is the source of truth. OpenSearch is the optimized search/read store. S3 contains prepared static aggregate data. Axis hides these storage details from middleware.

2. Background Synchronization

The scheduled job keeps OpenSearch synchronized with PostgreSQL. It should process changes incrementally rather than rebuilding the entire index on every run.

flowchart LR
    START[Scheduled Job] --> CHECK[Find Added / Updated / Deleted Records]
    CHECK --> READ[Read Required Source Data]
    READ --> PREP[Prepare Search Document]
    PREP --> EMB[Generate Embedding]
    EMB --> WRITE[Upsert / Delete in OpenSearch]
    WRITE --> STATE[Save Sync Checkpoint]
  1. Detect changes in the source database.
  2. Read only the required source data.
  3. Prepare the searchable document.
  4. Generate vectors for fields that support semantic search.
  5. Update OpenSearch.
  6. Save a checkpoint for the next run.

If searchable text changes, the affected document can be embedded again. If a source record is deleted, that deletion must also reach OpenSearch.

3. Embedding Flow

The embedding service is used during indexing and during semantic search. No LLM is required. The same embedding model should be used for documents and queries.

flowchart LR
    TEXT1[Document Text] --> EMB1[Embedding Service] --> VECTOR1[Document Vector] --> OS1[(OpenSearch)]
    TEXT2[User Search Text] --> EMB2[Embedding Service] --> VECTOR2[Query Vector] --> OS2[(OpenSearch Vector Search)]

4. Frontend Request Flow

The frontend communicates only with middleware. It does not need to know whether the result came from OpenSearch or S3.

flowchart LR
    FE[Frontend] --> MID[Middleware] --> AX[Axis] --> PLAN[Query Planner]
    PLAN --> OS[(OpenSearch)]
    PLAN --> S3[(S3)]
    PLAN --> EMB[Embedding Service]
    EMB --> OS
    OS --> OUT[Normalized Response]
    S3 --> OUT
    OUT --> MID
    MID --> FE

Structured search and filtering

Filters, sorting, pagination, ordinary text search and supported aggregations can be handled directly by OpenSearch. No embedding request is needed.

Semantic search

Axis sends the user's search text to the embedding service, receives a vector, and uses that vector for similarity search in OpenSearch.

Static aggregate data

Prepared dashboard aggregates can be generated by a background job and stored in S3. Axis can retrieve them instead of recalculating them during every request.

5. Query Planning

The query planner is the decision point inside Axis. It determines what type of backend operation the request requires.

flowchart TB
    REQUEST[Incoming Query] --> PLAN[Query Planner]
    PLAN --> STRUCT[Structured Search / Filter] --> OS1[OpenSearch]
    PLAN --> SEM[Semantic Search] --> EMB[Embedding Service] --> OS2[OpenSearch Vector Search]
    PLAN --> STATIC[Static Aggregate] --> S3[S3]

The planner selects the appropriate path; it does not replace the compilers or adapters.

6. Transformation Inside Axis

flowchart LR
    REQ[Request] --> VALID[Validation] --> MODEL[Internal Query] --> PLAN[Planning] --> COMPILE[Backend Query] --> EXEC[Adapter / Execution] --> NORMAL[Response Normalization]

Axis validates the request, converts it into its internal representation, plans the operation, builds the backend query, executes it and normalizes the result before returning it to middleware.

SQL compiler boundary: the SQL compiler remains in Axis because scheduled synchronization needs SQL access to PostgreSQL. It does not need to run for normal frontend reads when OpenSearch is the read store.

7. Static Aggregate Flow

flowchart LR
    SOURCE[Source Data] --> JOB[Aggregation Job] --> AGG[Precomputed Aggregate] --> S3[(S3)] --> AXIS[Axis] --> RESPONSE[Dashboard Response]

Static or infrequently changing aggregates can be prepared ahead of time and stored in S3.

9. Architectural Boundary

PostgreSQL is the source of truth. OpenSearch is the optimized read/search store. S3 is the prepared aggregate store. Axis is the abstraction layer between application requests and these storage systems.

The expensive work—indexing, embedding and aggregate preparation—happens in controlled background processes wherever possible. The normal user read path stays focused on fast retrieval.
