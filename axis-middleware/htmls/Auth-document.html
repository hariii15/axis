1. Purpose

Phase 8 makes Axis completely application-agnostic for security. The library never knows JWT structure, claim names, tenant IDs, user IDs, column names, Express, or auth libraries.

  • The middleware/application owns authentication and converts identity into a generic AxisContext.
  • Axis receives that context plus application-registered security mappings and establishes PostgreSQL session state before running SQL.
  • PostgreSQL RLS enforces the actual row filtering.
  • Caching is security-aware so one tenant/user can never read another tenant/user's cached result.
The golden rule: authentication happens in the middleware, authorization is enforced by Postgres. The library in the middle only translates — it never decides who anyone is.

2. End-to-end pipeline

Every protected POST /query follows this path:

HTTP Request ↓ Express middleware: Authorization: Bearer <JWT> ↓ verifyJwt(token, secret): signature + expiry + claims check ↓ createAxisContext(decodedJwt): JWT claims → generic AxisContext ↓ axis.query(queryJson, { context }) ↓ Validate → AST → resolve model → resolveSecurityContext (fail-closed) ↓ Cache lookup with security-aware key (HIT returns / MISS continues) ↓ Compile → SQL ↓ Database.transaction: BEGIN → set_config (SET LOCAL) → SQL → COMMIT ↓ PostgreSQL RLS uses current_setting('app.tenant_id', true) ↓ Rows → cache store under security-aware key → QueryResult

Architecture diagram

HTTP Request | Express Middleware Authorization header | Verify JWT | Decode JWT | AxisContext { tenant, user, roles } | AxisQueryEngine.query + context | Security Resolver (context × mappings) | PostgreSQL Transaction BEGIN / SET LOCAL / query / COMMIT | PostgreSQL RLS (tenant_id / created_by = context) | Compiled SQL (SELECT ...) | Database Result

3. Design rules

  1. JWT lives in middleware only.
  2. JWT verification lives in middleware only.
  3. JWT claim names live in middleware only.
  4. Axis only sees generic AxisContext.
  5. Axis never hard-codes tenant IDs, user IDs, or column names.
  6. Security mappings are registered by the application.
  7. PostgreSQL RLS enforces row security; Axis only sets session context.
  8. Security context is transaction-scoped (SET LOCAL semantics via set_config(..., true)).
  9. Missing required context fails closed — the query never executes.
  10. Cache keys include the configured security subset.
  11. Connection pooling never leaks context between requests.
  12. Axis stays framework-independent (no Express import).
  13. The existing JSON → Validator → AST → Resolver → SQL pipeline is unchanged.
  14. Non-security queries keep working when no security config is registered.

4. What was implemented

4.1 Generic AxisContext

axis/src/core/context/types.ts — the only context type the library knows:

export type AxisContext = Record<string, unknown>;

// Example application context:
const context: AxisContext = {
  tenant: "tenant-001",
  user: "hariharpradeep@gmail.com",
  roles: ["MANAGER"],
};

4.2 Security configuration types

axis/src/core/security/types.ts — registered once by the application, never hard-coded:

export interface SecurityMapping {
  contextKey: string;  // key in AxisContext, e.g. "tenant"
  column: string;      // app DB column, e.g. "tenant_id" (docs/RLS reference)
  sessionKey: string;  // PG session key, e.g. "app.tenant_id"
  required?: boolean;
}

export interface AxisSecurityConfig {
  mappings: Record<string, SecurityMapping>;
}
const axis = new AxisQueryEngine(database, {
  security: {
    mappings: {
      tenant: { contextKey: "tenant", column: "tenant_id", sessionKey: "app.tenant_id", required: true },
      user:   { contextKey: "user",   column: "created_by", sessionKey: "app.user_id",   required: true },
    },
  },
});

4.3 Security resolver (fail-closed)

resolveSecurityContext(context, config) reads each mapping, looks up context[mapping.contextKey], and throws SecurityContextError when a required: true value is missing — before cache or database are touched. Unknown context keys (e.g. roles) are ignored; optional mappings are skipped when absent; session keys are allow-list validated.

// Example failure — the query must NOT execute:
SecurityContextError: Required security context value "tenant" is missing.

4.4 Database transaction helper

Database.transaction(callback): acquire one pooled client → BEGIN → callback → COMMIT (or ROLLBACK, rethrowing the original error) → always release(). SET LOCAL state dies with the transaction, so pooled connections never leak tenant context.

4.5 PostgreSQL SET LOCAL (safe)

The executor runs inside the transaction, once per mapping:

SELECT set_config($1, $2, true);
// params: [sessionKey, sessionValue]

set_config(key, value, true) with is_local=true equals SET LOCAL. Keys are allow-list validated; values are bound parameters, so quote-containing input cannot inject.

4.6 Query engine integration

new AxisQueryEngine(db, { registry, cache, security })  // options shape
new AxisQueryEngine(db, registry, cache)               // legacy shape, still works

await axis.query(input, { context });  // QueryOptions { context?: AxisContext }

Pipeline per request: parse → AST → resolve → resolveSecurityContext → cache.get → compile → execute → cache.set. Security context is execution metadata; it never enters the AST.

4.7 Security-aware cache keys

buildCacheKey(query, { security }) mixes the canonical security subset into the digest. Empty/absent security preserves the legacy key, so non-security queries are unaffected:

Query A + tenant-001 → miss → DB Query A + tenant-001 → HIT Query A + tenant-002 → miss → DB (different key, no leak)

4.8 Middleware: JWT verification + AxisContext

All of this lives in the axis-middleware package (src/auth/) — never in the axis library:

// src/auth/auth.ts
verifyJwt(token, secret): DecodedJwt
createAxisContext(decoded): AxisContext
extractBearerToken(header): string
createAuthMiddleware(secret): Express middleware (sets req.axisContext)
requireAxisContext(req): AxisContext
class AuthError extends Error { statusCode }

Both claim shapes map to the same context: spec { sub, tenantId, roles? } and legacy { userId, tenantId, role? }.

// src/config.ts: jwtSecret: process.env.AXIS_JWT_SECRET ?? ""
// src/app.ts (inside createApp, only when jwtSecret is set):
axis = new Axis({ database, registry, cache, security: DEFAULT_SECURITY });
app.use("/query", createAuthMiddleware(jwtSecret));
// POST /query handler:
const result = await axis.query(input, { context: req.axisContext });
// errors: AuthError -> 401, SecurityContextError -> 403

6. PostgreSQL RLS setup

Application-owned — Axis never creates policies, it only sets the session context:

ALTER TABLE upeg.requisition_deails ENABLE ROW LEVEL SECURITY;

CREATE POLICY requisition_tenant_isolation
ON upeg.requisition_deails
USING (
  tenant_id = current_setting('app.tenant_id', true)
);

8. Ownership split

Library (axis) — generic, no middleware: core/context/types.ts (generic AxisContext), core/security/*, transaction helper, security-aware executor/engine/cache, tests/security/*. Removed: src/middleware/*, legacy JWT context files, the jsonwebtoken dependency, stale dist/middleware/*.

Middleware (axis-middleware) — owns auth, env, HTTP: src/auth/*, src/app.ts (DEFAULT_SECURITY + auth on /query + 401/403), src/config.ts (AXIS_JWT_SECRET), tests/auth.test.ts, tests/legacy-context.test.ts, the jsonwebtoken dependency.

9. Final API

// axis-middleware (owns auth): src/auth/auth.ts + src/app.ts
const decoded = verifyJwt(token, process.env.AXIS_JWT_SECRET!);
const context = createAxisContext(decoded);

const result = await axis.query(
  {
    model: "PurchaseRequisitions",
    metrics: ["newCount"],
    axes: ["department_name"],
    filters: [{ field: "status", operator: "equals", value: 1 }],
  },
  { context },
);
